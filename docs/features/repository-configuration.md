# Repository configuration

The Repositories drawer on the Block library tab lets an administrator manage the GitHub repositories that blocks and releases come from: add, edit, test and delete repositories, and set an access token per repository or one global token.

Related pages: [block-library.md](block-library.md), [add-extension-wizard.md](add-extension-wizard.md), [repository-layouts-and-builder.md](repository-layouts-and-builder.md), [roles-and-security.md](roles-and-security.md), [backend-and-browser-mode.md](backend-and-browser-mode.md).

---

## Requirements

**A repository has a name, a URL and an optional token.** The URL is a GitHub URL that may point at a branch and a folder, for example `owner/repo/tree/main/samples/blocks`. The form takes the part after `https://github.com/`. The items shown and built come from that path.

**Repositories are stored per tenant.** They are shared by every user of the tenant and survive a reload. Each user with permission sees the same list.

**Repositories have no enabled or disabled state.** Every configured repository is available in the Block library and the wizard. A value `enabled` that an older version stored is ignored, and it is dropped the next time the repository is saved.

**Add, edit, delete.**

- A new repository starts as a "Not saved" entry in the list. It is stored only when the user saves it. Cancelling discards it.
- Name and URL are required. The URL must form a valid URL after the GitHub prefix is added.
- Save is enabled for an existing repository only when something changed.
- Leaving with unsaved changes asks to discard them or keep editing.
- Delete asks for confirmation naming the repository.
- If the last repository is deleted, or none exists when the drawer opens, the form for a new repository opens.
- The list can be filtered by name, URL or id.
- Repository changes show a success alert and refresh the Block library items.

**Test connection.** The user can test the form values before saving. The test reaches the repository with the entered token (or the stored or global one) and reports success, or a specific message: the token is invalid or expired or not SSO-authorized (401), access denied or rate limit exceeded (403, 429), repository not found (404), or a generic connection failure. A token is optional for public repositories. Unauthenticated requests are limited by GitHub to 60 per hour per IP, a token raises this to 5000.

**The token is never shown again.** Once a token is saved, the form shows a masked placeholder. The real value is never put back into the form.

- Leaving the masked field untouched keeps the stored token.
- Typing a new value replaces it.
- Clearing the field removes it, so the repository falls back to the global token or to anonymous access.
- Changing the URL or the name of an existing repository clears the token field and shows a warning ("Changing the URL or name resets the PAT token. Enter the token again."). A token is never silently reused against a different repository.

**A global token is a fallback.** One tenant-wide token, saved separately in the drawer, is used for every repository that has no token of its own. A repository token always wins. Listing releases uses the same order as downloading (repository token, then global token, then none), so a release list of a private repository works with the global token alone. The form says which token applies: its own, the global one, or none (public repositories only).

**Token help.** The form tells the user how to create a token: scope `public_repo`, and enable SSO for the token when the organization requires it.

**Known limit: tokens are readable by users who can read the tenant option.** See Limitations.

## Implementation

### UI

[repositories-drawer.component.ts](../../analytics-ui/src/repository/drawer/repositories-drawer.component.ts) (`a17t-repositories-drawer`) is an in-page bottom drawer (not the Cumulocity drawer service) opened by the Block library tab. It uses a split view: the repository list on one side, the form on the other, and a global token form above the list. The form is a reactive form with `id`, `name`, `url`, `accessToken`.

- `urlValidator` prepends `https://github.com/` and checks that `new URL()` accepts the result. It does not check that the repository exists or that the host is GitHub (the prefix makes the host fixed). Use Test connection for that.
- The saved URL is `https://github.com/` plus the field. On load the prefix is stripped again, so the user edits the short form.
- New ids are generated by `createShortId()` (six letters and digits). The backend accepts only letters, digits, hyphens and underscores as an id.
- `hasFormChanges()` compares name and URL and handles the token specially: an existing token comes in as the masked sentinel, so only a new real value or a cleared field counts as a change.
- `warnAboutPATReset()` runs on change of name or URL, clears the token field and shows the warning. This matches the storage layer, which clears a token when the URL changes.
- Add, update and delete go through `RepositoryService` and afterward `updateHideInstalledFilter(hideInstalled)` is called to refresh the item state.

### Storage

[repository-config.service.ts](../../analytics-ui/src/shared/repository-config.service.ts) reads and writes the Cumulocity tenant options directly from the browser with `FetchClient` and `TenantOptionsService`. There is no second implementation through the backend: the backend's own configuration endpoints (`GET` and `POST /repository/configuration`) store the same options in the same format, so entries written by either side interoperate.

| Item | Where |
|---|---|
| Repository | Tenant option, category `analytics-management.repository`, key = repository id, value = JSON `{ "name", "url", "accessToken" }`. `accessToken` is left out when empty. |
| Global token | Tenant option, category `analytics-management.settings`, key `globalAccessToken`, value = the token. |

- **Listing** uses the category-scoped `GET /tenant/options/{category}`, which returns a flat key to value map. The generic `GET /tenant/options` ignores a category filter and would return every option of the tenant. A 404 means "none saved yet" and is not an error.
- **Parsing** drops an option that is not JSON or has no `url`, so unrelated options in the category do not appear as blank repositories. The token is replaced by the sentinel `_DUMMY_ACCESS_CODE_` when set, and by an empty string when not.
- **Saving** a list creates or updates one option per repository and deletes options of repositories that are no longer in the list. A write tries `update` first and falls back to `create`, because a plain create is rejected for an existing key. On save the sentinel means "keep the stored token"; the token is dropped if the URL changed; a real value replaces the token. The writes are sequential, not atomic.
- **Serialization.** `RepositoryService` runs add, update, delete and save through one queue, so two quick changes cannot overwrite each other from stale snapshots.
- **Token resolution** for a request: a real token in the repository object, else the stored token of that repository (looked up by id, never for a `temp-` id), else the global token, else none. The browser needs the real token for its direct GitHub calls (listing items, listing releases), so it reads the option itself, and for listing releases falls back to the global token like the service does (`getRepositoryAccessTokenOrGlobal`); the masked form value is never sent anywhere.
- **Backend side.** The backend loads the repository by id from the same option and uses the token server-side. The GitHub requests it makes are restricted to the configured repository: a URL for another host or another repository is rejected, so a stored token cannot be sent elsewhere. A test of a draft repository sends the entered token in the header `X-Repository-Access-Token` (never in the URL, so it stays out of access logs).
- **Permissions.** Writing options needs a tenant option management role in the browser. The backend route that writes the configuration requires the admin role. See [roles-and-security.md](roles-and-security.md).

### Limitations

- Tokens are stored in plain text inside the option value and the global token in the settings category. Any user who can read tenant options can read them. The migration notes call this a known limit: a hidden option type such as `credentials.*` would break the browser's direct GitHub requests.
- The URL check accepts any path under `https://github.com/`; it does not verify the shape `owner/repo`.
- Deleting a repository does not touch extensions that were built from it. Their build information keeps the repository id, name and URL (never the token).
